# Penny as a frontier customer-learning runtime

**Proposed extension, not current capability or authority.** The flagship plan makes Penny responsible for learning whether an intervention addressed a real customer problem. This extension identifies a failing goal in time to help, reproduces it against the real product, commissions credible changes, and carries them through authorized measurement. Penny becomes the owner-controlled research and intervention runtime around customer goals.

The proposed home and interaction rules are in [Penny's user journeys](user-journeys.md): Results, Learning and Needs you in the existing workspace; one actionable card only when a real choice or authority boundary needs an operator; quiet progress otherwise. The owner sets direction and a bounded source/effect grant once. Penny prepares the investigation and measurement details, then continues within scope. These are future behaviors, not a new dashboard or current app capability.

Give capable agents substantial product investigation and implementation work, and assess their output against explicit checks and observed customer outcomes. A proof checker can verify a formal result; software tests establish selected properties, but neither establishes customer meaning or improvement. Penny needs faithful task tests and observed outcomes.

## Three tempos, one evidence path

Penny can act quickly without pretending every model does every job. The product app emits only small, explicitly enabled semantic events needed for a named goal—such as `accountant_invite_denied` or `close_packet_completed`. The event contract specifies purpose, fields, retention, account linkage and allowed use. This is deliberate instrumentation, not passive session replay or broad visitor tracking. Deterministic code supplies identity rules, counting, dates, deduplication, budgets and authorization.

A fast typed model can evaluate permitted text or structured state against supplied choices, criteria and instructions. As documented on 27 September 2026, Jev's choice primitive selects among options supplied by the application; its model interface accepts text and JSON. Jev is a useful candidate for frequent, narrow judgments, not a text or code generator, independent sensor, source connector, or inventor of an unprovided option. [Models and state](https://docs.typesafe.ai/models), [choice](https://docs.typesafe.ai/primitives/choice). A fast generative dialogue model may draft a clarification; it is a separate capability from typed selection and frontier investigation. Penny should supply an explicit none or unknown outcome, retain sampled negatives and route novel signals to investigators. A fixed label set must never make a new need disappear. These model tempos and assignments stay inside the product; the owner sees evidence, uncertainty, consequence and a useful next action, not model selectors or agent orchestration. A recommendation is reasoned advice, while options remain unranked on `DEC-003` dimensions. Confidence describes a model output distribution, not an independent check; arithmetic, dates, indirection, distracting context and text generation are documented limitations. [Jev 1.13 limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13).

Frontier reasoning agents handle the cases that need invention: unfamiliar patterns, competing explanations, code inspection, new test design, and interventions that do not yet exist. They can operate as a team with RER and the product owner's coding agents: examine permitted evidence and actual source, create reproducible tasks, build competing implementations in isolated environments, run security and journey checks, and prepare a real experiment. A governed execution runtime then checks grants and effects at the point of action. Model confidence never expands authority.

Measure the full event-to-result path at realistic load and customer regions, including retrieval, preprocessing, escalation and rendering. Compare calibrated error and coverage, p50/p95 latency, cost per correct action and interruptions. Vendor claims or a fast model call do not establish Penny performance. Abstain or escalate when a quick decision misses its error budget.

## Make a goal executable

The central record is a customer's job and acceptable result, not an account score. “Close the books by the third business day with an accountant” carries its cohort, permitted signals, success definition, blockers, competing explanations, task steps and counterexamples. Observations, identity basis, interpretations, tests, decisions, code changes and outcomes remain separately versioned.

A reusable goal-to-test-and-outcome protocol is a concrete candidate for common source: it turns a goal into a bounded test, records what evidence can satisfy it, and carries that same definition into post-change measurement. It should be published from the repository that naturally owns the capability after real adoption proves its value. Penny owns the product's purpose, source selection, cohort and consent rules, decision and outcome record; no shared module can grant access or alter an edition's policy.

Ownership follows the actual systems: HappyToHelp owns conversations, Orbit CRM identity, the delivery tracker issue state, and the product repository its code and release identity. Penny receives selected, authorized evidence and explicit links, preserves unresolved identities, and owns the goal-to-outcome record. RER and owner agents execute source work.

## Two complete cases

**Repair a failing month-end journey.** A participating product has explicitly enabled invite and close-step events for the stated bookkeeping goal. A customer reports that their accountant cannot help. A fast model links the permitted denial event to an existing investigation protocol, while `unknown` outcomes and a sample of apparent non-matches still reach review. Penny preserves the customer's source, checks only an explicit account link, and commissions a frontier team to inspect the permitted docs and owner repository. The team reproduces the failure in a test tenant, then compares a role repair, an export-discovery change, and no change against the same task and security checks.

For a future pilot, the owner could already have issued a versioned grant covering that repository, isolated branches and tests, plus a small, expiring rollout to a named eligible cohort with a spend ceiling and rollback rule. Penny prepares the outcome measure and comparison from the stated goal and available records; it does not ask the owner to fill in technical fields. The candidate passes code tests and the rollout reduces invite denials, but the observed month-end completion rate does not improve; review shows many affected customers already used CSV successfully. Penny stops at the declared rule and reports that the interaction changed but the goal did not. It investigates export discovery only if that work fits the existing source/read grant; otherwise it preserves both findings and surfaces one card for the new scope. If the grant allowed only branch and test work, the system would stop before rollout and state the exact missing authority. It does not treat a passing build as a solved customer problem.

**Invent a new close workflow.** Across authorized support accounts and opted-in app events, people repeatedly ask to resend exports, clarify which version the accountant used, and confirm that corrections were incorporated. Existing labels call this “export” or “accountant access,” but an investigator sees a possible new job: hand off a complete monthly close packet and resolve questions in one place. Penny keeps the raw examples, checks whether this pattern is new and which customers it affects, and asks what evidence would distinguish a shared close workflow from a simpler export improvement.

Frontier agents build three real alternatives in isolated branches: a clearer CSV handoff, a read-only accountant packet, and a bounded shared close workspace, alongside no build. Task fixtures check permissions, revisions and recovery; consenting participants then try the workflows on their actual close tasks under the approved study protocol. The predeclared outcome is completion by day three without staff intervention or duplicate corrections; adverse access, correction and noncompletion measures remain visible. Suppose the shared workspace helps only new customers while established teams prefer CSV. Penny recommends a supported cohort-level configuration with a common codebase and owner-controlled limits. It does not create a permanent account fork, publish an account-specific promise, or generalize synthetic-user preferences into demand. Further extension follows only if evidence justifies it.

These examples are illustrative product cases, not customer evidence. Simulated users can find confusing steps or adversarial paths and improve a test, but they cannot supply demand, consent, interviews, votes or outcomes. Customer contact and production effects require purpose-specific permission and a preissued grant within the future edition contract.

## Learn without forgetting the limits

Penny saves useful mechanisms as evidenced, versioned protocols: applicability, examples, task test, allowed actions, failure modes, counterexamples, model/source versions and revalidation trigger. Another edition may reuse “accountant could not complete a handoff” only when its permitted evidence matches those conditions. If its customers already close with CSV, or its permissions differ, the protocol abstains and investigates anew.

Months later, another product reports “send this to my accountant.” Penny can reuse the handoff test, then a source release record reveals that export moved behind a new role check. That change invalidates the old explanation; Penny marks it superseded, preserves its evidence lineage, and tests the new path before reuse. If the source owner revokes the connection or erases the records, affected derived memory is retracted under policy. Restore or resume checks revocation and erasure state before re-indexing, and effect receipts prevent a prepared invitation or rollout from being repeated.

Runtime code supplies pause, checkpoint, cancel, resume and replay semantics: revocation prevents new reads, queued work stops at defined boundaries, replay cannot repeat effects, and erasure covers derived state and exports. A model can recommend a pause; code enforces revocation. In the existing operator workspace, **Results** includes negative and incomplete outcomes, **Learning** shows one active question and next check, and **Needs you** contains actionable decisions or true exceptions. Results and routine progress are informational; they do not create review chores. One card carries the recommendation, evidence, uncertainty, real preview, consequence and action. Pause, inspect actions/cost, correct, and disconnect controls stay discoverable without exposing schemas or orchestration.

## Authority and scope

This goes beyond Stage 3's scoped investigation, tests, prototypes and briefs. A future edition could grant agents permission to author and test code, then run an experiment or promote a verified change within policy. Each grant names sources, paths, effects, cohort/rollout ceiling, budget, expiry, stop conditions and rollback in plain language; Penny proposes and pre-fills those details so the owner does not design the measurement form. Runtime code records effects and enforces revocation. Work inside a grant does not need approval of each internal step; deployment, customer contact, external commitment and access expansion require deliberate grants for those classes. No answer means no new grant. Penny sends no routine progress alerts; the owner may opt into one digest, and a consequential card gets at most one reminder before its predeclared deadline or grant expiry. At expiry only the affected effect stops, with other in-scope work continuing.

Nothing here changes the current `CONTRACT.md`, `seed.json` or release authority. Implementation in Penny still starts with the required TanStack Start conversion and source reconciliation. Isolated, authorized experiments can test these hypotheses before the full baseline is built; the main product path does not need every baseline feature in place to learn whether this new direction works. Before a real Penny stage, reopen only its bounded clauses and manifest effects, add direct tests, and preserve the flagship plan's stable identity, equal-operator access, source custody, consent, erasure, non-ranked alternatives, public projections and no-silent-commitment guarantees.

## The decisive pilot

Run both cases with real permitted evidence. Compare Penny with a strong frontier coding/research agent on the best-configured incumbent workflow and on scratch. Record every attempt: novel-signal recall (including sampled negatives), false links and abstentions, test fidelity, real outcome numerator/denominator, null/adverse results, permission stops, attention of owners, staff and customers, setup/correction/recovery work, each notice and reminder, spend, full workflow p50/p95, and time to useful action and measured outcome. Predeclare thresholds for attention, contact, correction burden and notifications; these are targets, not measured performance. Separate synthetic test behavior from customer outcomes.

The extension succeeds only if Penny finds new needs without losing known ones, produces faithful reproductions and credible interventions, and reaches an improved real outcome or useful negative decision with less total cost, elapsed time and owner attention than the strongest alternative. Report every attempt. Disprove or narrow it if novelty recall is poor, tests fail to predict tasks, changes do not transfer, escalation erases the fast tier's value, routine grants require constant rescue, or burden rises without verified value. Model capability claims cannot substitute for this comparison.
